# Shared filing rules

Read this skill before using `file-issue` or `file-pr`. Those skills define
issue- and pull-request-specific checks; this file defines the common standards.

## Target, identity, and authorization

- Determine the exact `owner/repo`. Use the repository named by the user; do not
  silently default to the current checkout when the target is ambiguous. Ask
  before filing if the correct project cannot be established.
- Verify the GitHub identity used for attribution with `gh api user`; do not
  expose tokens or credentials.
- Do only the GitHub action the user requested. A request to prepare a PR, commit
  changes, or create a PR does not authorize pushing. Never push, force-push,
  change remotes, or switch credentials without explicit authorization. If a
  requested PR depends on a push that was not authorized, prepare the local
  materials and state what authorization is still needed.

## Content

- Read and follow the target repository's current template and contribution
  instructions. Preserve required headings, comments, checkboxes, and ordering;
  do not replace them with a generic body.
- Write concise, human-readable content for maintainers. Include only relevant,
  verified facts and exact reproduction or validation evidence. Link to logs,
  CI, and artifacts rather than dumping long output. Separate observation from
  hypothesis; do not invent root causes, test results, severity, or changelog
  conventions.
- Include the repository-required AI disclosure. By default, prepend:

  ```text
  _Generated by an AI assistant on behalf of @<user>._
  ```

  Replace `<user>` with the verified GitHub login. Follow a target repository's
  explicit alternative placement/wording if it has one. Do not disclose private
  context or include credentials.
- Keep each issue or PR focused on one concern. Do not bundle unrelated fixes
  or add speculative implementation plans to a bug report.

## Verification

- After filing or posting, verify the returned issue, PR, or comment URL and
  confirm the final body when practical. Report the URL, target repository, and
  any action that was not performed.
- If an action fails due to permission or authorization, stop and report it.
  Do not try another account, credential, remote, protocol, or force-push path.
