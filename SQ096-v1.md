# Abstract

This specification addresses a critical gap in operational assurance of charmed distributed systems: the insufficiency of an active/idle charm state from the control plane (hooks executed successfully) vs. the actual operational state and self-validation of the data plane to ensure the workload is functional and integrations are working correctly.

We propose a Charmed Workload Probes Framework that enables deep validation of the data plane through a phased, pragmatic implementation strategy that:

1. Delivers immediate value without requiring charm modifications \- Phase 1 Non-Invasive / Black-Box \- utilizing “reference probes” to test charms from the outside given the charm context and its integrations without changing the code of the charm.  
2. Provides a migration path for charm engineering teams \- Phase 2 White-Box  \- migrating validation logic inside the charms with minimal charm code changes.   
3. Establishes a sustainable, ecosystem-wide pattern \- Phase 3 charm-integration-library \- the team owning the charm embeds the tests into their integration library, while the others implementing the provided interface use the validation logic from that library for that interface.

The framework supports CI/CD validation (lifecycle tests, chaos testing, upgrades, migrations), production diagnostics (SRE troubleshooting), and automated periodic status checks in Phase 3 driven by the charm – all unified through a single abstraction layer.

This specification is built on top of the initial ideas outlined in [SQ059 - Endpoint Probes](https://docs.google.com/document/d/1U_2ZIJx-EyROgCtfkt5KNbuf0GWiFfp-xdePRctB9zg/edit?tab=t.0#heading=h.v228s8hnqd53)

# Rationale

## The “Active \!= Operational” Gap

Current state:

* Juju's “active/idle” status indicates that charm hooks executed without errors or exceptions;  
* Automated testing validates only that “juju status” reaches this state;  
* No verification of actual workload functionality or integration health.

Real-World failures:

* Database charm shows “active” but authentication credentials are misconfigured  
* Frontend application is “active” but cannot connect to its backend due to firewall blocking;  
* Storage integration is “active” but permissions prevent file writes  
* Message queue is “active” but consumers cannot subscribe due to ACL misconfiguration;  
* Backend application is “active” but consumers experience API failures due to exhausted shared memory.  
* Unit shows active but \`systemctl\` shows core services down

Impact:

* QA blindspots: matrix testing produces false positives (tests pass, production fails);  
* Production Incidents: SREs cannot quickly validate deployment health without manual testing;  
* Triage overhead:  
  * Engineers manually investigate every “red” status with no automated classification;  
  * Engineers must know which “active/idles” are untrustworthy or spend a lot of time tracing error back to root cause  
  * A lot of time spent on red herrings   
* Upgrade risk: no systematic way to verify data continuity across version changes.  
* Absence of confidence in the status reported by *juju status* vs actual state, accumulated over time.

## Limitations of Existing Approaches

Manual testing:

* Requires “juju ssh” access and workload-specific client tools;  
* Not automated; results are not captured in CI/CD pipelines and test management systems;  
* Knowledge is siloed in individual engineers' runbooks.

External integration tests:

* Test logic lives in separate repositories from charm code;  
* No standard interface;   
* Difficult to run against production models

Kubernetes probes (for K8S charms only):

* Only validate process liveness (socket open), not application logic  
* Machine charms have no equivalent mechanism  
* Cannot test cross-charm integrations

# Specification

## Core principles

* Uniform interface:  infrastructure interacts with a single, standardized contract regardless of implementation;  
* Progressive enhancement: start with zero-touch validation, migrate to embedded probes over time;  
* Separation of concerns: validation logic is interface-driven, not charm-specific;  
* Production safe: default to read-only checks; write operations require explicit opt-in.

## User Stories

The list is not exhaustive.

* TUS-1:  
  As a charm developer,I want to import a standard test for my interface,  
  So that I do not have to write custom integration validation logic or worry about how to connect to the upstream.  
* TUS-2:  
  As a QA engineer I want the CI to automatically fail if an upgrade causes data loss.  
  I expect the test runner to manage the upgrade lifecycle and use the charm probe action to verify data integrity before and after the upgrade.  
* TUS-3:  
  As an SRE (Customer) I want to debug a production outage by running validate-integration action.  
  I expect a clear output telling me if the app can reach the database without the need to manually “shell” into the system.  
* TUS-4 as an SRE I want to have periodic and automated checks on my juju controller that would validate the health of a system and expose the relevant metrics.


## Validation contract

* All validation mechanisms expose the same Juju Action interface:  
  * Action definition:

```
yaml
validate-integration:
 description: "Validate workload data plane and integration health"
 params:
   target:
     type: string
     description: "Specific integration endpoint to validate (e.g., 'database', 'ingress'). Omit to test all."
     default: ""
   level:
     type: string
     description: "Validation depth: 'simple' (connectivity), 'deep' (read/write transaction)"
     default: "simple"
     enum: ["simple", "deep"]
   cleanup:
     type: boolean
     description: "Remove test artifacts after deep probes (canary data)"
     default: true
```

    

  * Output schema:

```json
{
 "status": "PASS|FAIL|WARN",
 "timestamp": "2026-02-05T14:32:11Z",
 "target": "database",
 "level": "deep",
 "results": [
   {
     "check": "connectivity",
     "status": "PASS",
     "duration_ms": 45
   },
   {
     "check": "authentication",
     "status": "PASS",
     "duration_ms": 120
   },

     "check": "write_transaction",

 ],
```

## Phase 1: Reference Probes \- Current State (alternative \- juju exec)

Timeline: Q1 2026  
Target: Legacy, Stable and 3rd party charms

### Solution

Deploy lightweight "Reference Probes" charm that test target charms from the outside by exercising their interface contracts as a real consumer would:

* Deploy *target* and *neighbor* charms and probe-*interface* charm alongside them;  
* Relate *target:interface* to *neighbor:interface*  
* Run *validate-integration* on probe-*interface*  
* The probe attempts to write/read from the target.

Pros: works immediately on any charm implementing interface. Can be developed and improved independently of charm release cycle. Backward compatible with previous charm releases.  
Cons: require maintenance of the separate project with such probes and updating them to the interface updates. Cannot inspect internal charm state \- black-box only. Extra units on the model.

## Phase 2: Transition SDK with minimal charm changes \- Transition state

Timeline: Q3 2026  
Target: Active development teams, community charms

### Solution

Provide a shared Python library (juju-probes-sdk) that charm developers can import to add validation actions with minimal change:

* Charm developer adds *validate-integration* action  
* Imports validation logic: *from juju\_probes import validate\_database*  
* Runs action directly on *target* application

Pros: fast execution without extra units deployment. Minimal changes to the charm code. Validation logic is centrally maintained. Can access internal charm state for deeper validation.  
Cons: requires charm modification. SDK must stay on par with the interface changes. Charms must release new versions to incorporate SDK updates.

## Phase 3: Native interface library support \- Target state

Timeline: Q4 \- Q1 2027  
Target: Core ecosystem, official interfaces

### Solution

Validation logic lives directly in *charm-integration-interface* libraries, maintained by charm engineering teams. When a charm imports an interface library it automatically gets probe capability.

Pros: Probe logic always matches the interface version. Validators are written by domain experts. Minimal changes to charms \- action handler wiring. Library upgrades without SDK dependency.

### Acceptance criteria

* All interfaces MUST provide *.validate\_integration()* method  
* Method MUST return the standard probe result schema  
* Validation MUST default to read-only (“simple” mode)  
* Write operations (“deep” mode) MUST use namespaced artifacts (“\_juju\_probe\_\*”)  
* A charm implements the *.validate\_self()* method that runs functional checks on the service after the integrations have been validated successfully.

## Test orchestration / CI integration

Test framework automatically selects the best validation approach:

```py
def verify_workload(juju, target_app):
   """
   Intelligent Probe Dispatcher
   """
   # STRATEGY A: Native (Phase 2 & 3)
   # Preferred: Fast, deep inspection of internal state.
   if "validate-integration" in juju.list_actions(target_app):
       return juju.run_action(target_app, "validate-integration")

   # STRATEGY B: Reference probes (Phase 1)
   # Fallback: External validation via sidecar.
   interfaces = juju.get_interfaces(target_app)
  
   if "mysql_client" in interfaces:
       probe = juju.deploy("ch:probe-mysql")
       juju.integrate(target_app, probe)
       juju.wait_for_idle()
       return juju.run_action(probe, "validate-integration")
  
   raise TestError("No native probe or reference client available for this app.")

```

## Further extended test scenarios

Upgrade Safety:

* Deploy v1.  
* Run Probe (Deep) \-\> Writes "Canary Token".  
* Refresh to v2.  
* Run Probe (Deep) \-\> Verifies "Canary Token" persists.

Model Migration:

* Run Probe on Source Model.  
* Migrate Application.  
* Run Probe on Target Model (verifies connectivity remains after IP re-addressing).

Idempotency:

* Relate \-\> Unrelate \-\> Relate.  
* Run Probe (Ensures clean tear-down and re-setup of credentials).  
* Deploy \-\> Remove \-\> Deploy to the same model  
* Run Probe

Resiliency:

* Deploy charm  
* Reboot machine / delete pod  
* Run probe to ensure self-healing:  service is back successfully


High availability:

* Deploy charm in an HA configuration  
* Run probe that system is HA

Chaos Recovery: the runner handles the “Break \-\> Probe \-\> Fix \-\> Probe” loop.

## Risk Mitigation

#### Adoption Risk

Risk: Charm developers don't adopt probe framework

Mitigation:

* Phase 1 requires zero adoption (works immediately on legacy charms)  
* Phase 2 SDK reduces implementation to small amount of  lines of code  
* Provide CI/CD integration that "just works" (automatic strategy selection)  
* Publish success metrics showing reduced triage time  
* Make probe support a requirement for "Recommended Charm" status

#### Production Data Corruption

Risk: Deep probes accidentally corrupt production data

Mitigation:

* All probes use namespaced artifacts (\_juju\_probe\_\* tables/keys)  
* Default to level=simple (read-only connectivity checks)  
* level=deep requires explicit opt-in via action parameter  
* Transactional writes with immediate rollback where supported  
* Clear documentation: "Run deep probes in staging first"  
* Action parameter cleanup=true (default) ensures artifacts are removed

#### False Positives/Negatives

Risk: Flaky network causes probe failures, creating CI noise

Mitigation:

* Test orchestrator implements retry logic with exponential backoff  
* Single probe failure \= WARNING (logged but doesn't fail test)  
* Persistent probe failure (3+ retries over 60s) \= ERROR  
* Probes include detailed error context for debugging  
* Separate "transient failure" from "persistent failure" in reporting

#### Resource Consumption (Phase 1\)

Risk: Deploying probe charms increases cloud costs

Mitigation:

* Probe sharing: Single probe validates multiple apps with same interface  
* Probes are minimal (single container, minimal resource requests)  
* Cleanup policy: Remove probes after test suite completion  
* Phase 2/3 migration eliminates probe deployment overhead

#### Version Skew (Phase 2\)

Risk: SDK falls out of sync with interface evolution

Mitigation:

* SDK uses dynamic relation data inspection (not hard-coded schemas)  
* Comprehensive test suite validates SDK against all interface versions  
* Phase 3 migration moves logic to authoritative interface libraries  
* Deprecate Phase 2 SDK once Phase 3 achieves critical mass

#### Maintenance Burden

Risk: Maintaining probes across 4000+ endpoints is unsustainable

Mitigation:

* Focus on top 50 interfaces (covers 80% of deployments)  
* Phase 3 distributes maintenance to interface owners  
* Standardized protocol reduces per-interface effort  
* Probe logic is reusable across all charms using same interface
